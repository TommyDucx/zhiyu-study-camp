# ADR-0002：以学习引擎作为领域接缝

- 状态：已接受
- 日期：2026-11-22
- 决策者：项目维护者

## 背景

原型中的 `openCard`、`claimChest`、`redeem` 等 DOM 事件函数直接修改三套状态：卡片进度、每日委托、奖励账本；同时负责弹出 toast、刷新整个页面。奖励是否重复、宝箱是否可开、连续天数是否跨月，都只能通过浏览器手工验证。

这类逻辑最容易在迭代中产生“刷新后多领一次”“改状态刷日常”的静默错误，也正是应该通过**接口**测试的部分。

## 决策

将领域行为收敛到一个 `Learning Engine` **模块**，通过小接口提供：

- `openDocument`
- `completeDocument`
- `checkIn`
- `openChest`
- `redeem`
- `snapshot`
- `normalize` / `reconcile`

`openDocument` 永不发奖励；只有阅读器确认“从顶部滚动到底部”后才调用 `completeDocument`。领域模块不接触 DOM 或存储，变更操作返回 `effects`，由 UI 转成反馈。奖励幂等性通过内部 `awarded` 账本实现，不暴露给调用方。

## 后果

正向：

- 同一个 `engine.js` 同时被浏览器和 Node 测试使用；
- UI 不再复制“奖励是否已发”的判断；
- 新增成就和奖励是修改数据，不是复制业务分支；
- 可以在无浏览器环境下测试重复、边界与跨日规则。

代价：

- UI 必须接受并处理事件数组，不能直接改状态；
- 旧数据迁移需要 `normalize` 持续维护；
- 引擎成为高杠杆模块，接口改动必须补测试。

## 不采用

- **把规则留给 UI**：无法测试，且不同入口容易产生重复奖励逻辑。
- **引入完整框架/状态库**：当前单页、单人本机的状态复杂度尚不值得额外运行时依赖；深层原生 JS 模块足以承载。
